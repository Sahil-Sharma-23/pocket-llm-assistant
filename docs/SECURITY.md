# Security

Scope: the Go assistant, its scripts, and a Termux deployment on an Android
phone. Each control lists where it is enforced and which test proves it.
"Residual risk" items are not mitigated. Report vulnerabilities privately
through GitHub's *Report a vulnerability* (security advisories) on this
repository rather than in a public issue.

## Threat model

| Actor | Capability | Main concern |
|---|---|---|
| Web page in the phone's browser | Can send requests to `127.0.0.1` (DNS rebinding, CSRF) | Using the dashboard to approve or trigger actions |
| Other apps on the phone (no root) | Can connect to loopback TCP ports | Reading data via the API; driving llama-server |
| Telegram users other than you | Can message the bot if they find it | Using the assistant or approving actions |
| Content the model reads (web pages, notes) | Can contain instructions (prompt injection) | Getting the model to perform unwanted actions |
| Someone on the same Wi-Fi | Can reach ports bound to all interfaces | Termux `sshd` |
| Physical access / backups | Can read files if the device is unlocked or rooted | Data at rest |

## Controls

### Network exposure
- **The API and dashboard bind only to loopback.** A non-loopback `server.addr` is a
  config error (`config.validateLoopbackAddr`; tests `TestValidate`,
  `TestRunFlags/lan_bind_refused`; verified on-device: `PA_HTTP_ADDR=0.0.0.0:8787` → exit 2).
- **Host-header allowlist** (loopback names only) defeats DNS rebinding
  (`api.localHostOnly`; tests `TestRoutes/rebinding_host_rejected`; verified on-device: 403).
- **llama-server binds 127.0.0.1.** Its host and port are derived from
  `llm.base_url`, which must be loopback, and `--host`/`--port` are rejected in
  `extra_args` (`TestValidate/host_in_extra_args`).
- **Telegram uses outbound long polling only**; no webhook or inbound port.

### Data leaving the device
- **The LLM client can only dial loopback addresses.** A dialer hook runs after DNS
  resolution, so even a misconfigured URL cannot send a prompt elsewhere
  (`llm.loopbackOnly`; test `TestLlamaRefusesNonLoopback`). There is no cloud
  fallback in the code.
- What *does* leave the device, by design:
  - Research: search queries go to Wikipedia and DuckDuckGo, and fetched URLs are contacted.
  - GitHub API requests.
  - Configured monitors.
  - **Telegram messages**, which pass through Telegram's servers. Bot chats are
    not end-to-end encrypted. Use the dashboard for content that must never
    leave the phone.

### SSRF (model-proposed URLs)
- `web_fetch`, `web_search` and `http_check` use a **public-internet-only
  dialer**. It rejects loopback, RFC 1918, link-local, CGNAT and unspecified
  addresses after DNS resolution and on every redirect, and allows only the
  http/https schemes (`research.publicOnly`; tests `TestPublicOnlyClientBlocksLocal`, `TestIsPublicIP`).
- The model therefore cannot reach the dashboard, llama-server (8080), sshd or LAN devices.
- Monitors that *you* configure use a normal client, so LAN targets work.

### Permission enforcement (the LLM cannot bypass checks)
- A tool's permission level is fixed in Go (`tools.Spec.Permission`). The model
  supplies only a tool name and arguments; `agent.Executor` looks the
  permission up in the registry.
- Each agent may call only its allowlisted tools. Anything else is denied and
  logged (`TestToolOutsideAgentIsDenied`).
- Arguments are strictly decoded: unknown fields are rejected, so the model
  cannot smuggle `"permission": "read"` or similar (`TestSmuggledArgumentsRejected`,
  `TestPrepareValidation`). Typed validation follows.
- SENSITIVE calls (`task_delete`, `knowledge_delete`) **always** create an
  approval and never execute directly. Consequential WRITE calls
  (`reminder_cancel`) do the same (`TestSensitiveToolNeedsApprovalAndRunsOnce`,
  `TestNeedsApproval`).
- **Approval summaries are generated by Go code** from validated arguments and
  database lookups (for example *Permanently delete task #3 "Pay rent"*), never
  from model text, so the model cannot disguise an action.
- **At-most-once execution:** `pending → approved → executed|failed` transitions
  are atomic SQL updates. Concurrent approvals (Telegram button plus dashboard)
  cannot both win (`TestApprovalLifecycle`). Approvals expire (24 h default).
  An approval interrupted by a crash is marked failed and **not** re-executed
  (`TestNewCreatesPrivateDirsAndRecovers`).
- Slash commands go through the same executor and permission path.

### Telegram
- Only `telegram.allowed_user_ids` are served, private chats only. Approval
  buttons from other users are refused (`TestBotFlow`, `TestCallbackFromStrangerRejected`).
- Unknown users get one reply per hour telling them their ID (rate-limited to avoid amplification).
- The bot token is read from the environment only and **redacted** from every
  error (Go's `url.Error` embeds the full URL) (`TestTokenRedacted`).
- The update offset is persisted *before* handling, so a crash skips an update
  rather than replaying a side-effecting request.

### Dashboard
- Every POST requires a per-process HMAC CSRF token, and any `Origin` header
  must be same-origin (`TestCSRFProtection`).
- `html/template` auto-escaping is in place (`TestPagesRender` checks that an
  injected `<script>` is escaped).
- Headers: `Content-Security-Policy: default-src 'self'; script-src 'none'; frame-ancestors 'none'`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`.
- Request limits: 64 KB form bodies, 64 KB headers, server read/write/idle timeouts.

### Secrets
- There are no secrets in config files. Config holds only the *names* of the
  environment variables. `configs/secrets.env` is git-ignored, and
  `scripts/start.sh` **refuses to load it unless its mode is 600 or 400**.
- The dashboard's config page shows only whether each token is set.
- Logs never contain message text, prompts or tokens. Inference logs record
  token counts and timings only.

### Data at rest
- The database, backups and logs are mode 0600, and directories are 0700,
  inside Termux's app-private storage (unreadable by other apps without root).
- Android file-based encryption protects the data when the device is locked.
  There is no additional application-level encryption (residual risk below).

### Availability and resource abuse
- One inference at a time, a queue of 4, then an explicit "busy" error.
- A free-memory floor applies before starting the model or running inference.
- Tool timeouts, a run timeout (10 min), and job timeouts.
- Restart limits: the watchdog allows at most 6 restarts per hour with
  exponential backoff; the llama-server supervisor backs off to 5 minutes.

### Supply chain
- Go dependencies: `modernc.org/sqlite` (pure Go) and `golang.org/x/net/html`,
  plus their transitive modules. **`govulncheck ./...` with Go 1.27.3: "No
  vulnerabilities found."** Under the earlier Go 1.26.0 toolchain it reported
  36 standard-library CVEs, which is why `go.mod` pins `toolchain go1.27.3`.
  Inside Termux the Makefile forces `GOTOOLCHAIN=local` (upstream toolchains
  cannot resolve DNS on Android), so keep Termux's Go current with
  `pkg upgrade golang`.
- Model: the default comes from Google's official repository; the small model
  for low-RAM phones comes from `unsloth`. Both are SHA-256 verified against
  pinned hashes before use.
- Termux APKs (guided setup): official `termux/termux-app` and
  `termux/termux-boot` GitHub releases only, with the SHA-256 checksum
  published with each release verified before install.

## Residual risks and recommendations

1. **Prompt injection via web content.** A fetched page can tell the model to
   do something. Impact is bounded: the Research agent has only read tools plus
   `research_save` (adds a note tagged *research*), and any destructive action
   needs your approval with a Go-generated summary. Misleading *answers*
   remain possible; research answers are prefixed "From the web:".
2. **Other apps on the phone** can reach `127.0.0.1:8787` and `:8080` directly,
   because Android does not isolate loopback between apps. CSRF protects only
   browser-originated POSTs, and GET pages can be read. A malicious installed
   app could read the dashboard or use llama-server. Mitigation (future):
   per-install API token or a Unix socket in app-private storage. Install only
   apps you trust on this phone.
3. **Termux sshd** (optional, development only; the guided setup does not
   install it). Termux's sshd listens on all interfaces by default. If you use
   it, set `ListenAddress 127.0.0.1` in `$PREFIX/etc/ssh/sshd_config` so it is
   reachable only over USB `adb forward tcp:8022 tcp:8022` or from apps on the
   phone, use key authentication only (do not set a password), and run
   `pkill sshd` when you are not developing.
4. **Telegram is not end-to-end encrypted.** Avoid sending secrets through the bot.
5. **No application-level encryption at rest** beyond Android FBE. A rooted or
   forensically imaged unlocked device can read `data/assistant.db` and backups.
6. **`min_free_mem` checks race with other apps.** Memory can drop after the
   check. llama.cpp's mmap'd weights degrade gracefully, but the
   low-memory killer can still kill the processes; the watchdog and
   supervisor restart them.
